# Seeded Review and Demo Data Strategy

## Purpose

Seeded review/demo data should make local and review-environment workflows easier to inspect without using real shutdown schedules, real Project files, customer data, or production-like seed data. This document defines the strategy only. It does not add seed data, migrations, app code, source files, generated artifacts, or runtime seeding behavior.

Microsoft Project remains the schedule authority. Seeded data must support review of Shutdown Tracker import/export surfaces; it must not introduce scheduler logic, CPM, critical path, float calculation, resource levelling, recovery scheduling, automatic date movement, a live Project feed, or uncontrolled Project write-back.

## Current Baseline

The API already has a guarded review project bootstrap that can create or reuse one synthetic project when explicitly enabled:

```text
SHUTDOWN_TRACKER_REVIEW_PROJECT_BOOTSTRAP_ENABLED=true
```

That bootstrap creates project metadata only. It does not create source files, import batches, snapshots, imported tasks, export batches, live execution records, evidence, demo users, generated artifacts, or Project files.

The repository also has approved synthetic import/export fixtures under `fixtures/import-export/`. Those fixtures are test fixtures, not database seed data.

## Data Boundaries

Allowed future review/demo data:

- Synthetic project metadata with neutral names.
- Synthetic source-file metadata derived from approved synthetic fixtures.
- Synthetic import batches and parse summaries that match approved expected-output JSON.
- Synthetic imported snapshot rows derived from approved synthetic fixtures.
- Synthetic task lineage review rows for re-import review scenarios.
- Synthetic export preview batches and lines that exercise approved leaf-task progress/actual fields.
- Synthetic audit events for the review/demo actions the seeder performs.
- Text-only manifests describing the seeded dataset.

Prohibited review/demo data:

- Real shutdown schedules or real Microsoft Project files.
- Real MPP, XML, MSPDI, XER, ZIP, PDF, DOCX, screenshots, or generated exports.
- Real work orders, contractors, vendors, people, locations, assets, costs, commercial notes, or site names.
- Production tenant/customer setup.
- Secrets, credentials, provider configuration, or object-store connection strings.
- Generated MSPDI/XML artifacts committed to Git.
- Live execution/task-event demo data before task event APIs and tables exist.
- Scheduler-like fields or outputs generated by Shutdown Tracker.

## Seeding Mode

Future seeding must be explicit, local/review-only, and disabled by default. Suggested environment shape:

```text
SHUTDOWN_TRACKER_REVIEW_DEMO_DATA_ENABLED=false
SHUTDOWN_TRACKER_REVIEW_DEMO_DATASET_ID=synthetic-review-basic
SHUTDOWN_TRACKER_REVIEW_DEMO_DATA_RESET=false
```

Seeding should not run from database migrations. Migrations define schema only; review/demo data belongs in an explicit local command, runner, script, or test fixture setup path.

The `review` profile currently boots without PostgreSQL and should stay smoke-only unless a later deployment profile explicitly provides a database and opts into review/demo data.

## Dataset Metadata

Every future seeded row should be traceable to a synthetic dataset. Use metadata where available:

```json
{
  "synthetic": true,
  "allowed_use": "review_demo_only",
  "demo_dataset_id": "synthetic-review-basic",
  "fixture_id": "synthetic-basic-wbs"
}
```

Dataset manifests should be text-only and include:

- Dataset ID and name.
- Source fixture IDs.
- Expected row counts by table.
- Expected import/export states.
- Whether reset is supported.
- Confirmation that real project data is absent.
- Human review date or reviewer for any sanitized source, if sanitized data is ever approved.

## Recommended Dataset Sequence

1. `synthetic-review-basic`
   - One synthetic project.
   - One synthetic source-file metadata row.
   - One import batch with parser summary metadata.
   - One parsed and accepted imported snapshot using neutral task/resource/assignment names.
   - No live execution state and no export artifact.

2. `synthetic-review-lineage`
   - Two synthetic accepted snapshots for the same project.
   - Concrete task lineage links with existing review-state values.
   - No automatic lineage matching.

3. `synthetic-review-export-preview`
   - One accepted synthetic snapshot.
   - Draft export preview lines covering eligible leaf-task progress/actual fields and ineligible summary-task lines.
   - Approval/export states using existing enum values only.
   - No generated artifact unless the worker handoff is explicitly run in a local review flow.

4. `synthetic-review-round-trip-metadata`
   - Text-only manual Microsoft Project reopen/verification metadata for a synthetic export artifact.
   - No committed generated MSPDI/XML artifact or screenshot.

Live task execution, evidence uploads, handover notes, offline queues, and mobile field workflows should wait until their product APIs and audit rules exist.

## Reset and Idempotency

Seeded review/demo data should be safe to rerun:

- Use dataset IDs and metadata to find existing synthetic rows.
- Prefer idempotent upsert-like behavior for stable review datasets.
- Provide an explicit reset option for local disposable databases.
- Never delete rows without filtering to the selected synthetic dataset.
- Never reset or mutate rows that are not marked synthetic review/demo data.
- Keep visible product states in existing enums; do not add seed-only statuses such as `demo`, `queued`, `running`, or `completed`.

## Relationship to Fixtures

Fixtures and seeded data are related but separate:

- Fixtures live under `fixtures/` and define safe test inputs or expected outputs.
- Seeded data lives in a local database and should be generated from approved fixture metadata or safe synthetic code paths.
- Generated export artifacts remain temporary and must not be committed.
- Real Project files must not be copied into the repository or transformed into demo seed data.

The first preferred source fixture for future seeded import/review data is `synthetic-basic-wbs`.

## Implementation Sequence

1. Keep the existing review project bootstrap as project-metadata-only.
2. Add a guarded source/import/export review smoke script that can run validation-only checks now and richer ID-driven checks later.
3. Add a text-only review/demo dataset manifest format.
4. Add a local-only seeded-data command or runner guarded by explicit configuration.
5. Seed synthetic import metadata and parsed snapshot rows from approved expected-output data.
6. Seed synthetic import review and lineage scenarios using existing status/review-state values.
7. Seed synthetic export preview scenarios using existing export batch status values.
8. Run the source/import/export review smoke script against the seeded dataset.

Each implementation step should include tests proving no real data, generated artifacts, scheduler logic, Project write-back, or seed-only product statuses were added.

## Review Checklist

Before committing any future seeded-data implementation or manifest:

- Confirm the data is synthetic or fully sanitized and review-approved.
- Confirm no real Project files, generated exports, screenshots, binaries, secrets, or customer data are staged.
- Confirm seed data is disabled by default and not run from migrations.
- Confirm seeded rows are marked synthetic and scoped to a dataset ID.
- Confirm reset logic cannot touch non-synthetic rows.
- Confirm only existing product status enums are used.
- Confirm Microsoft Project remains the schedule authority and no scheduler/write-back behavior is introduced.
